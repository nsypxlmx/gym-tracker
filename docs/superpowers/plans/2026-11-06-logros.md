# logros Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the logros trophy case to TRCK3R: 77 core badges plus the seasonal *diciembre de hierro*. They are computed by replaying history, unlocked quietly in retrospect, toasted live during a workout, and shown in a third datos segment.

**Architecture:** Everything lives in `index.html`, the single-file classic script, as a `/* ==================== LOGROS ==================== */` block placed just before `let DB;` (line 546). It holds a declarative catalog (`LOGROS`), one pure chronological replay (`replayLogros`), and a sync layer that writes `DB.logros` and decides on toasts (`syncLogros`). UI functions render the segment, tile sheet, toast and summary rows. Emblems are drawn procedurally to cached data-URLs.

**Tech Stack:** Vanilla JS in one HTML file, localStorage, and a service worker. Tests use Node 24's built-in `node:test` with the `playwright` 1.62.1 library (its Chromium is already in `~/.cache/ms-playwright`).

**Spec:** `docs/superpowers/specs/2026-11-06-logros-design.md`. The section numbers (§) below refer to it. Read it alongside this plan: the catalog tables in §2 and the rule definitions in §3 are the source of truth for every badge's `title`, `req`, `grade` and test.

## Global Constraints

- All UI copy is in Spanish and lowercase, as in the rest of the app. Badge titles and `req` strings must match spec §2 verbatim.
- Points: bronce 10 · plata 25 · oro 50 · platino 200. Core totals: 26 B / 30 P / 20 O / 1 X = 77 badges, 2,210 pts.
- Weights are stored in kg. Thresholds with a kg/lb pair use the current unit's value, compared against `conv(kg)` (§3.3).
- Demo data (keys ≤ `DB.settings.demoUntil` while it's set) never counts (§3.1).
- Badges are never removed from `DB.logros` (§4.4).
- Emblem colors are fixed and appear only in logros, the toast and the summary. Everywhere else, the color system stays as it is: `--accent` for brand, `--success` only for PRs and completed sets, `--danger` only for destructive actions (§5.3).
- Never break boot: every `syncLogros` call made from boot, import or history edits is wrapped in `try/catch`, and a failure logs `console.warn("logros", e)` and continues.
- Do not touch `KEY` (`gymtracker_uni_v1`), the appId, or the existing tab migration in `render()`.
- Work on branch `logros`, not `main`. Commit messages are in Spanish, use the `feat(logros): …` style, and end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Never deploy, meaning never push to `~/AppDev/gym-tracker`, unless the user asks. Each Netlify build costs credits.

## Review Focus

1. **Malformed history:** sets with `kg:""`, reps like `"8-12"`, an exercise without `sets`, or a body weight stored as a string. The app must still boot and render logros; the replay skips what it can't parse. Pinned in Task 7.
2. **Opening logros mid-workout, then finishing:** the summary must still list every badge earned in that session, even though opening the segment set `seen:true`. Pinned in Task 10, using `s.logros`.
3. **Checking a set, unchecking it, then checking it again:** exactly one toast. A badge that's already stored never toasts again. Pinned in Task 10.
4. **A lb user:** a stored 100 kg squat is 220.5 lb, which must **not** give 2 plate club (225 lb). Pinned in Task 3.
5. **A session that runs past midnight:** a set checked at 00:20 in a session that started at 23:30 dates its live unlock to `curKey()`, which is yesterday, not today. Pinned in Task 10.
